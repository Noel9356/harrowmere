# Architecture

The kernel owns three concerns: component lifecycle, the event bus and the permission system. Everything else is a module behind a capability it publishes, and mods consume exactly the same capabilities. No kernel file knows GLFW, Vulkan, or windows exist — and no kernel file knows any module by name or any capability by meaning: modules are anonymous capability providers that describe themselves through static plugin descriptors, mods are anonymous consumers, and the kernel only mediates between them. Nothing is registered anywhere — neither modules nor capabilities; a module exists in a run exactly when an active mod requires a capability it provides. This document is the system map and the cross-cutting models; every module's internals live next to its code in `modules/<name>/README.md`.

## Capability surfaces

A capability is a pure virtual interface plus a stable name, e.g. `LoggerCapability` with `capabilityName == "logging"`. The capability's vocabulary lives in a header published by the module that PROVIDES it — `modules/logging_stdout/logging_capability.hpp`, `modules/window_glfw/window_capability.hpp`, and so on. There is no central contract directory: the provider owns its types, consumers include the provider's header directly, and the header is the single source of truth on both sides. Adding a capability means touching the module that provides it, never a shared tree. In CMake each module declares an `engine_capability_<name>` INTERFACE target that carries its include path and nothing else: a consumer links that target to compile against the capability without linking the provider's implementation binary, so the include graph in the build files IS the capability graph. A consumer compiles against a capability even when the provider that implements it is excluded from the build — the demand then fails at startup with a precise diagnostic instead of a compile error.

### Families and implementations

Capability names come in two shapes. A **family name** (`renderer`) is implementation-agnostic demand: "I need frame rendering, whichever implementation is installed". A **family member** (`renderer.vulkan`) is one implementation of that family, named after it. A requirement matches exactly first; a family requirement with no exact provider is satisfied by the single active member of that family, and two active members are an ambiguity that only a `[providers]` selection resolves. A requirement that names a member (`renderer.vulkan`) matches that implementation exactly — that is how a mod declares it NEEDS one specific backend. The shipped tree uses both shapes, and every provider declares the member its implementation actually delivers: `window.glfw`, `input.glfw`, `renderer.vulkan`, `scripting.lua`, `logging.stdout`, `lighting.pbr`, `screenshot.png` and `profiler.cpu` are implementation-bound members their modules provide, while mods require the families — which is why the demo mod never names GLFW or Vulkan even though both run underneath. A capability with no implementation variety behind it can still be a concrete, descriptive name: technique modules provide demand markers named after the technique and variant they deliver (`pbr_direct_diffuse`, `screen_space_radiance_cascades`, `world_space_radiance_cascades`) instead of the abstract radiance layer they fill, so a mod's demand list reads as the pipeline it assembles.

This is also the answer to "does the engine expose platform-specific capabilities?": yes — as family members. The portable surface every consumer is encouraged to use is the family; the implementation-bound member is visible, nameable, and picked either by installing only one implementation or by a `[providers]` selection. Script mods never see any of it: their surface is the Lua bridge (`../mods/README.md`, section "Portability").

### Names are opaque; acquisition is a pull

Capability names are opaque to the kernel: it matches requirement strings against provider declarations and never interprets what a capability means. The semantics live entirely in the provider's published header and its consumers. The one exception the kernel could have had — resolving a script mod's host — is not one: the package declares `host_capability` (one of its own requirements), and the kernel resolves that provider like any other requirement.

Acquisition stores nothing. `ComponentContext::acquireCapability` checks the permission (`capability.<name>`, derived from the requirement that pulled the component in) and then PULLS: the kernel walks the constructed components, finds the provider of the exact name — or of the family member that satisfies it — and calls that provider's `capabilityPointerFor` hook at the moment of the call, every time. There is no capability registry, no stored implementation table, and no construction-time population step; the construct phase only VERIFIES that every declared capability returns an implementation. Consumers cast the returned pointer to the interface they compiled against (the provider's published header); the kernel stays type-blind end to end. When several components consume one capability they pull the same provider object, so sharing costs nothing — there is simply nothing to duplicate.

The WALK behind the pull is what the kernel caches, not the pointer. While the component set is frozen — the construct phase completed, the first `stop()` not yet begun — the classification of a capability name (which records provide it exactly, which satisfy it as family members, under which member names) is computed once per distinct requested name and answered from a small per-name index afterwards (one entry per distinct name, scanned linearly - a run resolves only a handful of distinct names, so a scan of short string compares is cheaper than hashing and stays allocation-free); while the set is still flipping (construct in progress) or tearing down, the same walk runs live. Nothing about the answer changes: the classification is a pure function of the component set, and the implementation pointer is still pulled from the declaring provider's hook at the moment of every call, so a provider that changed what its hook answers between calls is answered with what it answers NOW. A frame-time acquisition therefore costs one small-index lookup plus one virtual call - and no allocation on any path it can take - while the records-times-declarations string-compare walk remains the construct phase's cost, not the frame's.

**Multi-provider acquisition** (`acquireEachCapability`) is the plural form of the same pull: it resolves EVERY active implementation of the name - exact providers first, then family members - each pointer pulled from its declaring provider at call time. The singular acquire fails by design when several providers resolve one name (the assembly must pick in `[providers]`, so a silent pick never depends on scan order); the plural form is the consumer stating "I want all of them", which turns a family into an extension point several mods can fill at once. Zero providers resolve to an empty vector - a plural request with zero implementations is a valid state, not a failure. The permission model is unchanged: the same `capability.<name>` grant covers the whole resolution.

Published capability headers are held to a portability rule, enforced mechanically at configure time: each module's `CMakeLists.txt` runs `engine_guard_capability_header` (from `cmake/capability_header_guard.cmake`) on the headers it publishes, and a header that starts including a graphics, windowing, or platform header (Vulkan, OpenGL, GLFW, X11, Win32) fails the configure. Module implementations keep their specifics behind opaque handles — the window capability deals in `void*` presentation surfaces and extension-name strings, so a renderer made from Vulkan and one made from OpenGL are indistinguishable behind the capability. The same discipline keeps glm (the module implementations' linear algebra library) off the published headers: capability vocabulary is plain data (float arrays), a mod compiles against a capability without inheriting a math library, and GLM's compile-time configuration (`GLM_FORCE_DEPTH_ZERO_TO_ONE`) is owned by the one `engine_glm_bindings` wrapper every module links through. Script mods see nothing else at all (`../mods/README.md`, section "Portability").

## Capability demand: how modules get activated

Nothing is registered anywhere — not in the app, not in the kernel, not in a configuration file — and nothing enumerates what may load. Activation is demand-driven, computed once at startup from static declarations:

1. **Module plugins describe themselves.** Every plugin binary in the modules directory exports one descriptor (name, factory, static provided/required capability lists). The kernel reads descriptors without creating instances. The descriptor scan runs through a runtime descriptor cache (`module_plugins.cache` next to the executable, a derived file a run rewrites as needed): a binary whose size and modification stamp match the remembered record contributes its descriptor without being loaded at all, so a startup only loads the plugins the demand closure will actually instantiate - new, changed and demanded binaries are always read from the file itself, which stays the ground truth. Deleting the cache file is always safe; the next scan rebuilds it.
2. **Mods are the sole demand roots.** Every active mod package becomes a component; its `capabilities` list states what it consumes, and a script mod's `host_capability` names which requirement its host must satisfy.
3. **The closure runs transitively.** Each demanded capability activates the plugin(s) that provide it — exact name matches first, then the members of the demanded family (honoring a `[providers]` selection when one applies) — and an activated plugin's own requirements demand further providers — the renderer brings `window` and `logging` with it, for example. A family demand satisfied through a member also marks the member as demanded, so a provider consulting the closure about its own capability sees the demand that activated it.
4. **Only then are instances created.** Plugins nobody required are never instantiated and their binaries are released before any construct phase; an instance manifest must agree with its static descriptor (drift is a precise startup error), and the construct phase verifies each provided capability has an implementation behind it — nothing is stored, because acquisition pulls from the provider at call time.

A requirement no available component satisfies fails startup with one precise diagnostic naming the consumer, the capability and the available alternatives. A run with no active mods loads zero modules: the engine kernel starts, publishes nothing, and exits cleanly. Startup work scales with what the run actually uses — a mod that does not require the `screenshot` capability never loads the screenshot module at all.

## Components, modules, mods

Modules and mods are both *components* in one dependency graph. Each declares a `ComponentManifest`: name, version, provided capabilities, required capabilities, optional capabilities, required permissions. The resolver treats every component uniformly, and the capability directions are one rule short of symmetric:

- module depends on module (screenshot requires renderer)
- mod depends on module (a native mod requiring logging and input)
- mod depends on mod (two mods sharing one capability - a native mod provides through `provides` in `mod.toml`, another mod or a module-consuming mod requires it)

The fourth direction is forbidden ON PURPOSE:

- **module depends on mod: refused.** A module may use capabilities provided only by other modules. The resolver refuses the declaration at startup with a precise diagnostic (naming the module, the capability and the mod it resolved to), and the acquisition boundary mediates the same rule at runtime: a module requester's answer never names a mod provider. The asymmetry is the trust boundary: mods are user-installed packages the engine risk-assesses and asks about, and a compiled-in module that could silently bind itself to one would turn every mod into an engine dependency. A mod that WANTS to serve modules has the wrong shape - move the capability's provider into a module.

### Capability directions

The rule in one sentence: **mods may use capabilities from modules and mods; modules may use capabilities from other modules only.** The resolver turns a module's requirement into a startup error when its resolved provider is a mod, filters mod providers out of every optional-capability and extension-point resolution a module participates in, and the kernel's acquisition boundary (all four acquire/probe/pull entry points carry the requester's kind) answers a module from module providers only. The application's own context - the composition root - is trusted and resolves against everything.

**Optional capabilities** (`optionalCapabilities`, `optional_capabilities` in `mod.toml`) state a *use-if-present* dependency: the component functions without the capability. They resolve through the same machinery as requirements — one provider, or the configuration's `[providers]` choice among several — and an existing provider is ordered before the consumer exactly like a requirement's. A REQUIRED capability with several providers and no selection stays the ambiguity startup error (a singular acquire would have to pick, and a silent pick would depend on scan order). An OPTIONAL capability that resolves to several members with no selection is the extension-point shape instead: every active member orders before the consumer, the plural acquisition (`acquireEachCapability`) takes all of them, and the singular probe answers "unavailable" - no pick ever happens, so no value can depend on scan order. The remaining differences: zero providers is a valid outcome (no edge, no diagnostic), the capability never joins the demand closure (an optional use never pulls its provider into a run that has no required use for it), and the derived `capability.<name>` permission still covers the acquisition. The consumer probes availability at construct time with `ComponentContext::isCapabilityAvailable` and degrades gracefully when the answer is no. The shipped worked examples: the lighting technique modules list `lighting` as optional and render emissive + sky transport when no light provider is active, and the scripting host lists the `scripting.lua_bridge` family as optional and installs every active module's bridge through the plural acquisition. For a MODULE consumer the direction rule filters the providers of an optional capability the same way it filters a required one: mod members are invisible, the module orders after the module members only, and an optional capability whose providers are all mods simply reads as unavailable.

A mod is therefore not a second-class plugin mechanism: it gets the same construction order, permission enforcement, and diagnostics as a compiled-in module - and where the two sides differ, the difference is the trust model below. Packages and the `mod.toml` schema: `../mods/README.md`.

**Component versions are informational identity.** Every module reports its version through `ComponentManifest::version`, every mod package through `mod.toml`'s `version` key (copied into the same field when the package becomes a component), and the graph report prints them next to each component's name. They move on their own schedules, separately from the kernel's product version, and they gate nothing: the compatibility gates are the module plugin ABI version (layout changes to anything a plugin binary compiles against - the kernel copies manifests out of plugin binaries, so a manifest field addition is a layout change) and the mod manifest's `engine_api`.

## Event bus

`EventChannel<Event>` stores handlers as cached function-pointer + user-data pairs in one contiguous vector; publishing is a linear scan with one indirect call per handler. No `std::function`, no queue, no allocation once the handler set is stable. Components cache a `channel<Event>()` reference once and publish with zero lookups.

**Subscriptions are priority-ordered.** Every subscribe overload optionally takes a priority: the handler vector is kept sorted by it at subscribe time (a stable insert - equal priorities keep subscription order, which is exactly what the plain subscription produces), so publish stays the same contiguous linear scan it always was and ordering is a subscription-time statement. Higher numbers dispatch first: a capture module can drain its completions BEFORE a consumer of its saved files at FrameBegin, a "react last" sink can summarize what the other handlers did. Ordering that used to depend on construct order is now explicit.

**Deferred delivery runs alongside the synchronous path, never instead of it.** `publishDeferred` is a vector append on the calling thread; `flushDeferredEvents` - driven by the composition root once per frame, next to the scheduler tick and the async completion drain - publishes the backlog as ordinary synchronous dispatches. FIFO within a channel, channels flush in creation order (a property of the assembly, never of hash layout), and an event deferred from inside a flush lands in the NEXT flush, so one flush is bounded by the backlog that existed when it started. What it buys: a handler can answer an event with an event of the same type without re-entering the scan it is running in, and a producer can batch its notifications into one visible point of the frame. The kernel flushes one last time at the top of stop(), so nothing deferred while the engine lived is lost. A run that defers nothing pays one relaxed atomic load per frame for the gate.

**Worker handoff queues carry events across the thread boundary.** `EventBus::createWorkerQueue<Event>()` returns a thread-safe queue whose `enqueue` any thread may call and whose flush the same frame-point drives: worker completions used to re-enter the single-threaded world one bespoke lambda at a time (and still may, through AsyncTaskDispatcher), while a worker queue moves the events themselves - the decode worker that finishes twelve textures enqueues twelve AssetLoadedEvents and never writes a capture-heavy completion. The queue's mutex is the only lock, exactly like the dispatcher's queue mutex, and an idle queue answers the flush with one relaxed atomic load instead of taking it - the frame path's cost on a quiet run is one load per queue, paid only by runs that created queues at all. The queues die with the bus's channels during stop.

The bus is single threaded by contract. Unsubscribing during dispatch is deferred to the end of the scan; `EventSubscription` RAII guards guarantee a stopped component never receives events through a dangling handler.

**Subscriptions are introspectable.** `EventBus::subscriptionReport()` renders one line per channel with handlers - the count and the priority span (or a note that every handler runs at the default priority in subscription order) - and the component graph report appends it, so a mod author can ask "who is listening, and how heavy is the scan I am about to join" and get the assembly's answer alongside who provides what.

## The frame clock

The loop heartbeat is a kernel event, not a renderer artifact. `EngineFrameEvent` (declared in `component_interface.hpp`, next to the other component-facing kernel events) is published by the composition root once per frame-loop iteration - after input polling, the kernel's two per-frame services and the opt-in reload poll, before the renderer's `renderFrame` - and carries the iteration's wall-clock delta and elapsed time. It decouples GAMEPLAY cadence from RENDERING cadence: the renderer's `FrameBeginEvent` stays the render-phase tick (capture queueing, UI new-frame work - anything that must run inside the rendered frame), while every simulation consumer - the scheduler's timers, the physics step, behavior trees, tweens, the game-state walk, the hot-reload drain, script frame handlers - ticks from the heartbeat. The practical consequence is that the whole gameplay layer runs headless: a server assembly (mods demanding `physics` and `scheduler`, no renderer) ticks exactly like a rendered one, because the tick source is the loop, not the GPU. Script mods join that story through the scripting host's optional `window` edge - a script mod loads into a window-less run exactly as it does into a rendered one (the one capability-backed host call, `engine.window_size`, answers `{0, 0}`). The rendererless pump's `idle_poll_ms` interval paces it; the heartbeat itself is free for runs whose components never subscribe (one subscriber-count check per iteration - no clock read, no publish).

**Fixed timestep is an opt-in second lane.** With `[engine].fixed_update_hz` > 0 the composition root also runs the classic accumulator loop and publishes `EngineFixedUpdateEvent` with the CONSTANT step delta after each heartbeat: simulation consumers that need frame-rate-independent determinism advance by exactly `1/hz` seconds per dispatch, with the catch-up burst clamped by `[engine].max_fixed_update_steps` (a stalled frame yields a bounded batch, never a spiral). Zero configured rate pays one branch per iteration. The variable heartbeat and the fixed lane are complementary surfaces, not competitors: render-shaped consumers keep the wall-clock delta, sim-shaped consumers take the step.

**Finite runs are a configuration key.** `[engine].quit_after_seconds` ends the loop after the given wall-clock time through the same clean-shutdown path a window close takes (exit 0): the headless smoke-test and CI shape - a run that needs no window, no kill signal, and reports success by its exit code. All three knobs live with the pacing keys, re-read on every live configuration reload.

**The heartbeat's delta is the whole gameplay layer's clock.** Every simulation module advances by the `EngineFrameEvent`'s `deltaSeconds` - the one delta the composition root measured for the iteration - instead of each reading a clock of its own inside its handler: one clock read per frame serves timers, physics, behavior trees and tweens together, every module sees the SAME delta (two runs with the same frame schedule tick identically), and a module with nothing to do returns at its empty check without touching any clock. The CPU-side frame cap (`[engine].max_fps`) waits with a sleep-then-spin shape - sleep through the bulk of the interval, spin the last millisecond on the clock with a PAUSE/YIELD hint so the tail stays exact without starving the sibling thread - so a capped run's frame times carry the scheduler's wakeup overshoot no longer; on Windows the capped run additionally requests the 1 ms timer resolution (`timeBeginPeriod`), without which the default ~15.6 ms system tick would push every sleep wake past its deadline. An uncapped run pays none of this.

## Kernel utilities

Kernel-side utilities round out the component surfaces:

- **AsyncTaskDispatcher** - off-main-thread work with main-thread completion (`post`, `postWithCompletion`, `drainCompletedTasks`). One dispatcher; `start()` is PARALLEL BY DEFAULT - it sizes the pool from the machine's hardware threads (`defaultWorkerCount()`, the same helper every engine component uses) - so batch work (image decode bursts, file IO, encode steps) spreads across the cores without a per-run decision. With more than one worker, dispatch ORDER between tasks is undefined (workers race the same queue), so posted tasks must be independent; an ordered caller - a self re-arming poll cycle - passes `start(1)` and keeps the historical single-worker behavior one argument away. Completions always re-enter the single-threaded world through the frame-path drain.
- **parallelFor** - fork-join parallel compute for one coarse batch (`kernel/include/engine/kernel/parallel_for.hpp`): `parallelFor(itemCount, chunkBody)` splits `[0, itemCount)` into contiguous chunks, runs them on the calling thread plus transient workers, and BLOCKS until every chunk has finished - the results are complete when the call returns, so no completion drain is needed. Sized by the same `defaultWorkerCount()` with a serial fallback for small batches; a throwing chunk is rethrown on the calling thread after the join. This is the shape for CPU-heavy batch work off the frame path (the renderer decodes its startup texture sets through it); a chunk should be at least roughly a millisecond of CPU time, and fine-grained per-frame fan-out belongs on an owned dispatcher instead.
- **MainThreadScheduler** - timed callbacks on the engine's one main thread: `scheduleAfter` / `scheduleEvery` (reached through `ComponentContext::scheduler()`) return RAII handles that cancel on release, the composition root's frame loop ticks the scheduler once per iteration, and a run that schedules nothing pays one empty-vector check per tick. Tasks run in deadline order with a whole-interval catch-up policy (a stalled frame yields one beat on recovery, never a burst), a task scheduled from inside a running task is first considered at the next tick, and the kernel clears the scheduler at the top of stop() so no timed callback fires during teardown. It is the timing twin of the dispatcher: blocking work leaves the frame path through `post`, periodic work returns to it through `scheduleEvery`.
- **Live configuration reload** - `EngineKernel::reloadConfiguration` re-assembles the layered configuration (parse-checking every file first, so a half-edited file is a refused reload, never a torn store), diffs the effective values and publishes `ConfigurationReloadedEvent` with the changed key paths. Opt-in through `[engine].config_reload_poll_seconds` (0 = the frame path pays nothing); the graph never re-resolves (see `docs/configuration.md`, "Live configuration reload").
- **ConfigurationWatchHub** - the per-key sugar over that event (`kernel/include/engine/kernel/configuration_watch.hpp`, instantiated per component): one subscription per component, one callback per watched key, fired only when the key's path is in the reload diff - changed or removed both count, world content never appears (the kernel reports scene edits as restart-required). The same keep-last-good re-read every hand-written handler was doing, minus the changedKeys scan.

## Communication latency model

The engine prioritises communication latency over decoupling, by measured design:

- **Module-to-module, mod-to-module and mod-to-mod calls.** Capability calls are direct virtual calls on a pointer acquired from the provider (one vtable indirection, no lookup, no locking). The event bus is the only fan-out medium and dispatches synchronously on the caller's stack; deferred events become exactly those synchronous dispatches at the flush point. Both paths are the minimum achievable for in-process, same-thread communication.
- **Measured, not assumed - and opt-in.** Recording is off by default (a normal run publishes thousands of events per second and its user does not want a data dump on shutdown; disabled, the bus never reads a clock, so measurement costs nothing). With `[diagnostics] latency_report = true`, every `publish()` records its dispatch duration into a per-channel fixed-size ring (no heap growth) and the app prints a per-channel mean/p50/p95/p99/max report plus the frame-time percentiles at shutdown.
- **Evaluated and rejected alternatives.** A bus whose ONLY path is a queue adds queueing latency and memory for decoupling no current feature needs; a threaded or async bus adds synchronization on every publish and re-opens the data-race surface the single-thread contract closed; an ECS would change data layout, not communication latency. That is why deferred delivery is a second, opt-in lane that ends in the same synchronous scan rather than a replacement, and why the worker handoff queue locks its own mutex instead of the publish path ever growing one. The architecture stays.

## Lifecycle

After resolving the graph, the kernel runs `construct` (acquire capabilities, subscribe to events — no backends), `start` (initialize backends, dependency order), and `stop` (reverse order). `validate()` is a pure dry run: configuration load, manifest build (including every `mod.toml` on disk), graph resolution, permission check — no backend is touched, which makes it CI-suitable.

Destructors are defensive: `stop()` no-ops when `construct` never ran, and the kernel destructor stops everything exactly once.

## Permissions

A component may only acquire capabilities it declared (`capability.<name>`) and may only write files with `filesystem.write`. The configuration can deny individual permissions per component; denial fails startup with a precise diagnostic. The app composition root is trusted; mods are subject to the same declared-grant model as modules. An acquisition without a grant is **blocked**: the engine refuses the access with a `ComponentAccessError` naming the component, the capability and the missing permission - during startup that fails the construct phase with the diagnostic, and at runtime it surfaces through the frame loop's error handling instead of ever handing out the capability.

### Risk advisories and the trust gate

The permission system enforces what it can; what it cannot enforce structurally, it makes visible - and gates. At discovery the kernel risk-assesses EVERY active mod AND every active module before any of their code is used; the signals are generic, never capability semantics: the component runs native machine code (mods; modules are machine code by definition, so the signal is theirs alone), it requests permissions outside the `capability.*` namespace (direct environment access such as `filesystem.write` - for modules this comes from the descriptor's `declaredPermissions`, read before the plugin binary is ever instantiated and verified against the manifest afterwards), or it acquires a broad set of capabilities. Every flagged component is announced as a warning on every run, trusted or not.

Warning alone is not the gate. A flagged component may be USED only when one of two things covers it: a standing trust decision in the configuration's `[trust]` section (`trustMods = [...]` / `trustModules = [...]` name trusted ids, `trustAllMods` / `trustAllModules` cover a kind), or the user's agreement at startup - the composition root connects the consent surface, an interactive run asks once per launch and proceeds only on yes, and a headless run that cannot ask fails startup with the trust instructions. The gate runs BEFORE anything flagged is used: no construct, no start, and no native mod library is even mapped before the trust question is answered. The `[trust]` section is assembly-owned: a package's shipped defaults cannot define it (a mod that could trust itself would defeat the gate), while a staged override (`--set trust.trustAllMods=true`) works like any key. The `--validate` dry run enforces nothing and asks nothing - it runs no construct phase - but its report lists which components a real run would ask about.

The risk signals stay structural by design: the kernel never interprets what a capability means. What the engine can enforce structurally (permissions, the capability directions) it enforces; what it cannot, it measures, announces, and puts behind an explicit decision.

## Extending

- New capability: publish its header from the module that provides it (`modules/<name>/<name>_capability.hpp`), implement it, and let consumers include that header. If several implementations of one family will exist, provide the implementation-bound member name in the plugin descriptor and let consumers demand the family.
- New module: create `modules/<name>` with its own `README.md`, its `CMakeLists.txt` (plus `shaders/` if it owns GLSL), and declare the module's name, factory, static capability lists and environment permissions (anything outside `capability.*`) in its `module_plugin.cpp` descriptor. That is the whole change - the directory is the only thing anyone touches: the build discovers every module directory (the module's CMakeLists brings its own `ENGINE_BUILD_MODULE_<NAME>` build switch), and the kernel discovers the built plugin at runtime by scanning the modules directory and reading the descriptor. No shared file lists modules, and no registration exists anywhere: mods activate the module by requiring its capabilities. The descriptor's module name must equal the name the module's manifest reports, and its environment-permission declaration must match the manifest's - the kernel verifies both agreements at startup.
- New backend for an existing family: implement the same published interface, provide the family member name in the descriptor, ship both providers; `[providers]` picks one at runtime (installing only one implementation needs no selection at all).
- New mod: create `mods/<id>/` with a `mod.toml`; see `../mods/README.md`. Every subdirectory of a mods directory IS a mod package - discovery reports a directory without a manifest instead of silently skipping it. A native mod adds its own self-contained `CMakeLists.txt` to the package directory - the build discovers it the same way module directories are discovered, and the kernel loads the built library from the package through the same plugin contract a module uses; the capabilities it PROVIDES are declared in `mod.toml`'s `provides` (the compiled manifest must agree).

### Documentation structure

Documentation lives next to the code it describes, in exactly two shapes: **one `README.md` per component** (each module and each shipped mod package) plus the mod authoring guide (`mods/README.md`), and **`docs/` for the cross-cutting guides** (architecture, building, configuration). A `README.md` documents identity, wiring, configuration keys with their shipped defaults and files; it stays a single-file guide. Content that serves several components at once never goes into a component README; it belongs in `docs/` where the other components can cite it.

### Configuration format: TOML, deliberately

Every configuration surface - `config/engine.toml`, scene files, mod manifests and mod `config.toml` - is TOML, and it stays TOML. The reasons are structural, not taste: comments carry load-bearing reasoning in the shipped configs (every demo knob documents why its value is what it is - JSON has no comment syntax); the dotted-path addressing (the in-kernel `stringAtPath` readers) maps one-to-one onto TOML tables; array-of-tables rows (`[[scene.objects]]`) are authored wholesale and replaced wholesale, which the merge semantics are built on; and the kernel carries exactly one parser (toml++) whose type errors report file and line. JSON would forfeit the comments, fork the configuration languages between configs and manifests, and buy nothing the engine needs.

### Mod system policy: the restriction set is the correctness minimum

Mods face as few restrictions as possible, and every restriction that exists must earn its place by protecting a correctness property - never by policy taste. The rules that survive that bar: the ABI version match (a mismatched binary would crash, not complain), unique ids and their restricted charset (ids become component names and configuration sections), package-contained scene paths (one package cannot claim content outside itself), the defaults-file ban on authority sections (`[engine]`, `[providers]`, `[permissions]`, `[diagnostics]`, `[scene]`, `[trust]` - a package that could deny permissions, drip world content or TRUST ITSELF would break the authority model), the capability direction rule (a module never binds to a mod-provided capability - see "Capability directions" under Components), and world-ambiguity failure (a world is never picked silently by filesystem order). Everything else is deliberately open: packages coexist freely, several may ship worlds side by side as long as the run names which one it wants, script mods may order after any component through `requires`, one `capabilities` entry provides both the graph edge and the acquisition grant, and unknown manifest keys are ignored (forward compatibility, not an error). The script bridge is small by design, and that is not a restriction on mods: native mods are the unrestricted path - C++ against engine headers, no bridge vocabulary, no sandbox - so the engine always offers full power next to the portable path.

### Asset ownership: the engine ships no content

The engine tree (kernel, modules, app, build scripts) is code only. Content lives in mod packages, and the split is enforced structurally, not by convention alone:

- **Content assets belong to mods.** Texture sets, world definitions and the defaults that point the renderer at them live in `mods/<id>/` (`assets/`, `scene.toml`, `config.toml`). The build copies each package's content into the runtime layout next to its entry; there is no engine-owned asset directory at all. A build without packages is a working engine that renders whatever the configuration defines - an empty sky by default.
- **Shaders are not assets.** A shader is the implementation of a rendering technique: it is written next to the module that owns the algorithm, compiled by CMake at build time, and fails the build loudly when broken. The runtime layout reflects this: SPIR-V lands in `runtime/shaders/` (build output, like the executable), not under any `assets` name.
- **The world has exactly one source.** A run's `[scene]` comes from an explicitly staged scene file, from the assembly, or from the single active content mod's declared scene file - never merged across sources (see `docs/configuration.md`, "The layer stack"), and never from a defaults file, which cannot define `[scene]` at all. Content mods coexist freely; the one-world rule fails startup only when no explicit source exists and two or more active packages claim the world - ambiguity is reported, never resolved silently.

The shipped `test_scene` package is the worked example: it owns the demo world, its texture sets, and the `renderer.texture_directory` default, and nothing in `modules/` or `kernel/` names it.
